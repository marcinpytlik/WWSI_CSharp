# EF Core Performance Lab — pierwsze wyniki referencyjne (22.11.2026)

**Źródło:** uruchomienie laboratorium na Dockerze przez prowadzącego; PowerShell `Run-Benchmark.ps1 -Take 100 -Repetitions 20`, 100 zamówień po 10 pozycji. Wariant `split` dodano **po** tych pomiarach, więc nie ma jeszcze wyników.

## Aplikacja (.NET 10 / EF Core 10)

| Strategia | Mediana 20 pomiarów (ms) | Polecenia SQL |
|---|---:|---:|
| N+1 | 114,93 | 101 |
| Include | 6,63 | 1 |
| Projection | 6,20 | 1 |

- N+1 / Include: około **17,3×** różnicy mediany.
- N+1 / Projection: około **18,5×**.
- Include / Projection: różnica mediany 0,43 ms, za mała, żeby bez dalszych badań wnioskować o uniwersalnej przewadze.
- Pierwszy pomiar Projection wyniósł 94,11 ms, kolejny 6,72 ms. Rozgrzewka każdej strategii nie wyeliminowała wszystkich kosztów pierwszego przebiegu.
- Stopwatch mierzy wykonanie operacji EF i tworzenie wyniku, **bez** serializacji oraz transferu HTTP.

## Query Store — odczyt historii zgromadzonej podczas laboratorium

| Query ID (historyczne, zmienne) | Typ | Executions | Avg duration (ms) | Avg CPU (ms) | Logical reads / execution | Logical reads total |
|---|---|---:|---:|---:|---:|---:|
| 7 | N+1 OrderItems | 4271 | 0,218 | 0,218 | 11 | 46981 |
| 143 | N+1 Orders | 21 | 0,098 | 0,098 | 3 | 63 |
| 144 | Include | 21 | 2,146 | 2,145 | 14 | 294 |
| 145 | Projection | 21 | 2,607 | 2,607 | 14 | 294 |

**Uwaga:** 4271 wykonań OrderItems przy 21 wykonaniach Orders wskazuje, że historia Query Store obejmowała więcej niż jeden znormalizowany przebieg. Nie należy porównywać sum `TotalLogicalReads` z powyższych wierszy jako kosztu tego samego zestawu żądań HTTP.

Dla pojedynczego żądania `take=100` można jedynie **oszacować** na podstawie średnich:
- N+1: 3 + 100 × 11 = **1103** logical reads;
- Include: **14** logical reads;
- Projection: **14** logical reads.

Stosunek 1103/14 ≈ **78,8×** jest modelem przy założeniu stabilności średnich, a nie niezależnym pomiarem wybranego żądania.

## Co wynika z eksperymentu

1. Tanie polecenie SQL wykonywane wielokrotnie może obciążać system bardziej niż pojedyncze większe zapytanie.
2. `Include` i `Projection` miały tyle samo średnich logical reads, choć projekcja pobierała mniej kolumn.
3. Projection nie musi być zawsze szybsza: w Query Store średni CPU był niższy dla Include, a w aplikacji nieznacznie krótsza była mediana projekcji.
4. CPU/duration silnika SQL nie są tym samym co czas mierzony przez aplikację.
5. Wyników z ilustracji promocyjnej nie traktujemy jako pomiarów.

## Dalszy eksperyment

- Wersja kodu po tych pomiarach dodaje `TagWith` (znaczniki `EFPLAB:`) i `AsSplitQuery()`.
- Zapisz snapshot Query Store **BEFORE** przez `sql/01_QueryStoreSnapshot.sql`.
- Uruchom kontrolowaną serię bez innych klientów; potem drugi snapshot **AFTER**.
- Uruchom `sql/02_QueryStoreDelta.sql`, aby policzyć przyrost wykonań, CPU i logical reads.
- Porównaj `split` z pozostałymi wariantami, a następnie przeprowadź eksperyment skalowania liczby zamówień (`take=10, 50, 100`).

Dopiero kolejne odczyty pokażą, czy zaobserwowane relacje utrzymują się przy większej liczbie danych.
